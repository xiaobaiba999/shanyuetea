## 1. 通用方法论：给骨架新增一个功能的「七步法」

以任意新功能（横幅/券/签到…）为例，写代码的顺序永远是：

```
① SQL 建表（本文档各节 DDL）→ ② entity 实体 → ③ Mapper 接口 → ④ Mapper XML →
⑤ Service 接口 + Impl → ⑥ Controller（挂 /user/** 或 /admin/**）→ ⑦ 重启 + curl 验收
```

| 步骤 | 放哪 | 规矩（照抄既有 Drink 系类即可） |
| --- | --- | --- |
| ① 建表 | 按本文档各功能节的 DDL 逐段执行（`USE shanyue;` 后） | utf8mb4；金额 `DECIMAL(10,2)`；时间 `DATETIME`；留 `create_time/update_time/create_user/update_user` 四列给 `@AutoFill` 切面自动填充 |
| ② 实体 | `shanyue-pojo` 的 `entity/` | `@Data @Builder @NoArgsConstructor @AllArgsConstructor`；字段与表列一一对应，靠 `map-underscore-to-camel-case` 驼峰映射（`link_type ↔ linkType`） |
| ③ Mapper 接口 | `shanyue-server` 的 `mapper/` | 接口加 `@Mapper`，方法名即 XML 的 `id`；参数多于 1 个要 `@Param` |
| ④ XML | `resources/mapper/` | namespace 写接口全限定名；VO 不在 `type-aliases-package` 扫描范围（只扫 entity），resultType 要写全限定名 |
| ⑤ Service | `service/` + `service/impl/` | 业务校验、事务边界（`@Transactional`）、抛业务异常（`BaseException` 子类）都在这层 |
| ⑥ Controller | `controller/user/` 或 `controller/admin/` | 路径挂 `/user/**` 自动被 C 端 JWT 拦截；挂 `/admin/**` 自动被管理端拦截 —— **不需要改任何拦截器配置** |
| ⑦ 验收 | curl | 见各功能包的「验收」小节 |

**三个必须遵守的安全底线**（主链路代码里已有样板，别丢）：

1. **当前用户 id 只从 `BaseContext.getCurrentId()` 取**（拦截器解析 token 后放 ThreadLocal），
   绝不信任前端传的 userId —— 防替别人下单/领券/签到；
2. **金额一律 BigDecimal**，`DrinkServiceImpl`/`ShoppingCartServiceImpl` 里已有服务端重算
   防篡改的样板（加购时单价=基础价+Σ规格加价，前端传的价格字段只做展示）；
3. **写操作先查后写**（购物车"同款同规格只加数量"、领券"一人一单"），并发兜底靠唯一索引。

```sql

    title       VARCHAR(64)  NOT NULL                COMMENT '主标题，如：桂花冰酿 · 秋日上新',
```

### 2.3 手把手步骤

**① 实体**（`shanyue-pojo/entity/Banner.java`）：

```java
@Data @Builder @NoArgsConstructor @AllArgsConstructor
public class Banner implements Serializable {
    private Long id;
    private String title;      // 主标题
    private String subtitle;   // 副标题
    private String theme;      // pine | gold | terracotta
    private String image;      // 图片 URL（空串=用主题渐变卡）
    private String linkType;   // page（预留 url）
    private String linkUrl;    // 跳转地址
    private Integer sort;
    private Integer status;
    private LocalDateTime createTime;   // @AutoFill 自动填充，见 2.5
    private LocalDateTime updateTime;
    private Long createUser;
    private Long updateUser;
}
```

**② Mapper 接口**（`mapper/BannerMapper.java`）：

```java
@Mapper
public interface BannerMapper {
    List<Banner> listEnabled();          // C 端：status=1 按 sort 升序
}
```

**③ XML**（`resources/mapper/BannerMapper.xml`）：

```xml
<mapper namespace="com.shanyue.mapper.BannerMapper">
    <select id="listEnabled" resultType="com.shanyue.entity.Banner">
        SELECT * FROM banner WHERE status = 1 ORDER BY sort ASC
    </select>
</mapper>
```

**④ Service**（`service/BannerService.java` + `impl/BannerServiceImpl.java`）：

```java
public interface BannerService { List<Banner> listEnabled(); }

@Service
public class BannerServiceImpl implements BannerService {
    @Autowired private BannerMapper bannerMapper;
    @Override public List<Banner> listEnabled() { return bannerMapper.listEnabled(); }
}
```

**⑤ Controller**（`controller/user/BannerController.java`，从零新建）：

```java
@RestController("userBannerController")   // bean 名带前缀，避免与将来的管理端同名冲突
@RequestMapping("/user/banner")
@Tag(name = "C端-轮播横幅接口")
@Slf4j
public class BannerController {
    @Autowired private BannerService bannerService;

    @GetMapping("/list")
    @Operation(summary = "C端-横幅列表（status=1 按 sort 升序）")
    public Result<List<Banner>> list() {
        return Result.success(bannerService.listEnabled());
    }
}
```

**⑥ 管理端横幅 CRUD（可选）**：照抄 `controller/admin/DrinkController.java` 的
增删改查+分页+启停套路，路径挂 `/admin/banner/**`（自动被管理端 JWT 拦截）。
banner 种子只有 3 条，管理页做出效果后自己插几条 `image=''` 的体验一下"渐变卡"兜底。

### 2.5 常见坑

- 新增/修改横幅想走 `@AutoFill` 自动填充 create_time？给 Mapper 方法加
  `@AutoFill(OperationType.INSERT)` 注解（参照 `DrinkMapper.insert` 的用法），实体字段名必须是
  `createTime/createUser/updateTime/updateUser` 四个固定名 —— 切面按名字匹配；
- XML 的 `resultType` 写 `Banner` 就行（entity 包在别名扫描范围），别写 `com.shanyue.vo.Banner`。

## 3. F2 会员等级（核心讲点：冗余字段 vs 聚合查询）

### 3.1 建表 DDL（user 表加两列）

```sql
USE shanyue;
ALTER TABLE user
    ADD COLUMN growth INT NOT NULL DEFAULT 0 COMMENT '会员成长值（方案 A 冗余字段：下单1元+2/签到+5；等级阈值 0/200/600/1200/2000 → Lv1~Lv5）' AFTER avatar,
    ADD COLUMN points INT NOT NULL DEFAULT 0 COMMENT '山月积分（签到+5；下单 1 元得 1 积分为演示口径）' AFTER growth;

UPDATE user SET points = 120, growth = 308 WHERE id = 1;   -- 演示用户：Lv2 青绿
```

- 等级阈值：**0 / 200 / 600 / 1200 / 2000 → Lv1 月白·新芽 / Lv2 青绿·抽枝 / Lv3 松风·亭亭 /
  Lv4 山岚·成林 / Lv5 入盏·知味**（演示用户 growth=308 → Lv2，进度 27%）；
- 成长值入账两处（每处一行 UPDATE）：**下单每 1 元 +2（挂 `OrderServiceImpl.paySuccess`）、
  签到 +5（挂 F5 的 sign）**。（原第三处"评价 +10"已随评价功能移除）

### 3.2 接口契约（对齐前端 level 页 / me 页真实消费的字段）

`GET /user/member/level` → `MemberLevelVO`：

```json
{ "level": 2, "levelName": "青绿", "levelTitle": "抽枝", "growth": 308,
  "nextLevel": { "level": 3, "name": "松风", "minGrowth": 600 }, "remainGrowth": 292,
  "progress": 27, "privileges": ["签到积分翻倍（+10/天）", "会员券包抢先领"],
  "levels": [ { "level": 1, "name": "月白", "title": "新芽", "minGrowth": 0, "privileges": ["..."] }, "…共5级" ],
  "growthRules": [ { "text": "下单消费 1 元 = 2 成长值", "icon": "order" },
                   { "text": "每日签到 = 5 成长值", "icon": "checkin" } ] }
```

- Lv5 满级时 `nextLevel: null`，前端文案自动切「已是最高等级」；
- `growthRules` 两条（评价行已移除）。

### 3.3 手把手步骤

**① 实体**：`entity/User.java` 补两个字段：

```java
/** 会员成长值（方案 A 冗余字段；DDL 见 3.1） */
private Integer growth;
/** 山月积分（签到+5） */
private Integer points;
```

**② 常量类**（`shanyue-common/constant/MemberLevelConstant.java`，等级阈值集中管理）：

```java
public class MemberLevelConstant {
    public static final int[] THRESHOLDS = {0, 200, 600, 1200, 2000};
    public static final String[] NAMES = {"月白·新芽", "青绿·抽枝", "松风·亭亭", "山岚·成林", "入盏·知味"};
    public static final int[] POINTS_BONUS = {5, 5, 10, 10, 10};  // Lv2 起签到积分翻倍
}
```

**③ Service**（`MemberLevelService`）：查 `userMapper.getById(userId)` 拿 growth →
循环 `THRESHOLDS` 落在哪个区间 → 算 `progress = (growth - 本级阈值) / (下级阈值 - 本级阈值)`
→ 组装上面的 VO（`levels` 全表 + `growthRules` 固定两条）。

**④ Controller**（`controller/user/MemberController.java`，从零新建）：

```java
@RestController("userMemberController")
@RequestMapping("/user/member")
@Tag(name = "C端-会员等级接口")
public class MemberController {
    @Autowired private MemberLevelService memberLevelService;

    @GetMapping("/level")
    @Operation(summary = "C端-我的会员等级视图")
    public Result<MemberLevelVO> level() {
        return Result.success(memberLevelService.view());
    }
}
```

**⑤ 两个入账点**（这是 F2 的灵魂，别只做查询）：

```java
// ① OrderServiceImpl.paySuccess 订单支付成功处（已有方法，追加一行）：
userMapper.updateGrowthById(userId, order.getAmount().intValue() * 2);  // 1 元 = 2 成长值
// ② CheckinService.sign 签到处（做完 F5 顺手挂）：
userMapper.updateGrowthById(userId, 5);
```

`UserMapper` 加一条动态 SQL：

```xml
<update id="updateGrowthById">
    UPDATE user SET growth = growth + #{delta} WHERE id = #{userId}
</update>
```

> 自增写法 `growth = growth + ?` 天然并发安全（无 lost update），比"先查后写"好 ——
> 这就是为什么不用先 SELECT 再 UPDATE。

### 3.4 方案对比（答辩必讲）

| | 方案 A：冗余字段（本工程） | 方案 B：视图聚合 |
| --- | --- | --- |
| 查询 | O(1) 一条 WHERE | 三表子查询聚合，订单量大后变慢 |
| 正确性 | 算错一次永久错（入账点漏挂就少加） | 永远自洽 |
| 适用 | 毕设/中小规模（推荐） | 报表型系统 |

## 4. F4 券包（毕设技术含量天花板：Redis 防超卖 + 一人一单）

> 黑马 Redis 实战「优惠券秒杀」章节的两板斧：**SETNX 一人一单 + Lua 原子扣库存**。
> 本功能 3 天里 2 天在写并发控制，1 天在下单事务用券。

### 4.1 建表 DDL（两张表）

```sql
USE shanyue;
DROP TABLE IF EXISTS coupon;
CREATE TABLE coupon (
    id               BIGINT        NOT NULL AUTO_INCREMENT COMMENT '主键',
    name             VARCHAR(64)   NOT NULL                COMMENT '券名称，如：新人礼·满30减8',
    type             INT           NOT NULL DEFAULT 1      COMMENT '类型 1 满减 2 折扣（演示秒杀券 type=1 + seckill=1）',
    threshold_amount DECIMAL(10,2) NOT NULL DEFAULT 0.00   COMMENT '使用门槛（满 X 元可用；0 表示无门槛，外送费不计入门槛基准）',
    discount_amount  DECIMAL(10,2) NOT NULL DEFAULT 0.00   COMMENT '满减金额（type=1 时生效）',
    discount_rate    INT           NOT NULL DEFAULT 100    COMMENT '折扣率（type=2 时生效，88 表示 88 折）',
    total_days       INT           NOT NULL DEFAULT 30     COMMENT '领取后有效天数（领取时算 expire_date）',
    seckill          TINYINT(1)    NOT NULL DEFAULT 0      COMMENT '是否秒杀券 0 否 1 是（秒杀券限量，领取走 Lua 原子扣减）',
    stock            INT           NOT NULL DEFAULT 0      COMMENT '秒杀总量（非秒杀券不限量，存 0）',
    remain           INT           NOT NULL DEFAULT 0      COMMENT '秒杀剩余库存（预热进 Redis 后以 Redis 为准，本列对账用）',
    status           INT           NOT NULL DEFAULT 1      COMMENT '状态 0 下架 1 上架（下架后 list 不展示、receive 报"券不存在或已下架"）',
    create_time      DATETIME               DEFAULT NULL,
    update_time      DATETIME               DEFAULT NULL,
    create_user      BIGINT UNSIGNED        DEFAULT NULL,
    update_user      BIGINT UNSIGNED        DEFAULT NULL,
    PRIMARY KEY (id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT = '优惠券模板表（F4）';

-- 券模板种子 4 张（与 mock-v2.js SEED_COUPONS 一致）
```

### 4.3 领券的三层防线（核心代码骨架）

```java
@Service
public class CouponServiceImpl implements CouponService {
    @Autowired private CouponMapper couponMapper;
    @Autowired private UserCouponMapper userCouponMapper;
    @Autowired private RedisTemplate redisTemplate;

    @Override
    public void receive(Long couponId) {
        Long userId = BaseContext.getCurrentId();          // 底线①：身份只从 token 取
        Coupon coupon = couponMapper.getById(couponId);
        if (coupon == null || coupon.getStatus() == 0) throw new CouponBusinessException("券不存在或已下架");

        // ---- 防线②：Redis SETNX 一人一单（挡住 99% 并发重复领取）----
        String oneKey = "coupon:received:" + userId + ":" + couponId;
        Boolean first = redisTemplate.opsForValue().setIfAbsent(oneKey, "1", Duration.ofDays(30));
        if (Boolean.FALSE.equals(first)) throw new CouponBusinessException("每人限领一张，请勿重复领取");

        try {
            // ---- 防线③：秒杀券 Lua 原子扣库存（判断+扣减一步完成，防超卖）----
            if (coupon.getSeckill() == 1) {
                String stockKey = "seckill:stock:coupon:" + couponId;
                Long remain = redisTemplate.execute(SECKILL_LUA, List.of(stockKey));
                // Lua: local r = redis.call('get', KEYS[1])
                //      if r and tonumber(r) > 0 then return redis.call('decr', KEYS[1]) else return -1 end
                if (remain == null || remain < 0) {
                    redisTemplate.delete(oneKey);           // 回滚占位，下次还能试别的
                    throw new CouponBusinessException("已抢光，下次早点来");
                }
            }
            userCouponMapper.insert(UserCoupon.builder()
                    .userId(userId).couponId(couponId).status(1)
                    .receiveTime(LocalDateTime.now())
                    .expireDate(LocalDate.now().plusDays(coupon.getTotalDays()))
                    .build());                             // 防线④：uk_user_coupon 兜底
        } catch (DuplicateException e) {                   // 唯一索引冲突 = 漏网并发
            throw new CouponBusinessException("每人限领一张");
        }
    }
}
```

> **为什么 Lua？** 「查库存→判断→扣减」三步在并发下会被插队（都查到剩 1 张、都扣成功 → 超卖）。
> Lua 脚本在 Redis 单线程里原子执行，判断+扣减不可分割。SETNX 同理防一人多单。
> 这两板斧是黑马秒杀课的核心结论，答辩能讲 15 分钟。

### 4.6 常见坑

- SETNX 占位失败后记得回滚占位 key（扣库存失败时 delete），否则用户永远"占着茅房"；
- Lua 里 `tonumber` 比较别写错：`tonumber(r) > 0` 才 decr，返回 -1 表已抢光；
- 预热：重启 Redis 后 key 会丢，秒杀前先 `SET seckill:stock:coupon:2 100`；
- **沙箱环境没装 Redis 时怎么办**：`receive` 的 SETNX/Lua 两层先注释掉、只留唯一索引兜底
  （单机演示不会并发超卖），答辩时把三层防线讲清楚即可。

### 5.3 BITMAP 三连核心代码

```java
@Service
public class CheckinServiceImpl implements CheckinService {
    @Autowired private RedisTemplate redisTemplate;
    @Autowired private UserMapper userMapper;

    @Override
    public Map<String, Object> sign() {
        Long userId = BaseContext.getCurrentId();
        LocalDate today = LocalDate.now();
        String key = "checkin:" + userId + ":" + today.format(DateTimeFormatter.ofPattern("yyyyMM"));
        int offset = today.getDayOfMonth() - 1;                 // 1 号 = 第 0 位

        // ① SETBIT 前先查今天这一位是否已签（GETBIT）
        Boolean signed = redisTemplate.opsForValue().getBit(key, offset);
        if (Boolean.TRUE.equals(signed)) throw new CheckinBusinessException("今日已签到，明天再来");

        // ② 签到 = 置位（SETBIT key offset 1）
        redisTemplate.opsForValue().setBit(key, offset);

        // ③ 积分入账 + 成长值 +5（等级翻倍联动 F2：查 user.growth 判断 >=Lv2 时 gained=10）
        int gained = 5;
        userMapper.updatePointsById(userId, gained);             // points = points + ?
        userMapper.updateGrowthById(userId, 5);

        return Map.of("gained", gained, "points", /* 查回 */
                      "streak", calcStreak(userId));
    }

    /** BITFIELD 取本月整条位串 → 内存里从今天/昨天往回数连续 1 的个数 */
    private int calcStreak(Long userId) {
        LocalDate today = LocalDate.now();
        String key = "checkin:" + userId + ":" + today.format(DateTimeFormatter.ofPattern("yyyyMM"));
        // BITFIELD key GET u<本月天数> 0 —— 取从第 0 位开始的整月位串（u = 无符号）
        Long monthBits = redisTemplate.execute((RedisCallback<Long>) con ->
                con.bitField(key.getBytes(), BitFieldSubCommands.create()
                        .get(BitFieldSubCommands.BitFieldType.unsigned(today.lengthOfMonth()))
                        .valueAt(0L)));
        // 从今天（或昨天）往回数：bit & (1L << n) != 0 表示那天签了
        // （跨月连续还要读上一个月的 key）
        return 0;  // TODO 按上述位运算实现
    }
}
```

> **为什么 BITMAP 而不是表？** 一个用户一个月 31 位 = 31 天，只占约 4 字节；
> 100 万用户一个月也就 4MB。`BITCOUNT` 算本月签到数、`BITFIELD` 取位串算连续天数，
> 全是 O(1)/O(位宽) 操作 —— 黑马签到课的结论，答辩讲"空间对比 VARCHAR 日期列表"。

## 附录 B：自测时踩过的真实坑（前车之鉴）

1. **购物车 add 的载荷别带 number** —— ShoppingCartDTO 只有 drinkId/setmealId/drinkFlavor/
   specSelected 四个字段，带多余字段 Jackson 默认直接抛未知异常（这是课程口径：数量由
   "同款同规格只加数量"在后端累加，前端不传）；
2. **specSelected 必须是 JSON 数组字符串**（不是"大杯/冰"这种自由文本）：
   `[{"groupId":4,"groupName":"杯型","optionId":9,"optionName":"大杯","priceDelta":3}]`，
   服务端会解析后校验 optionId 是否属于该饮品的合法选项（跨饮品的 optionId 会被拒：
   "包含非法规格选项"——这就是防篡改样板）；
3. swagger 分组名是中文：在线文档分组地址是 `/v3/api-docs/管理端接口`（URL 编码），
   不是 `/v3/api-docs/admin`；离线契约文件统一用根目录 `openapi.json`（v2 功能移除后
   64 路径 / 75 操作，与在线 `/v3/api-docs` 完全一致，直接导入 Apifox 即可）；
4. **mvn 重新打包前先停掉运行中的 jar 进程** —— 运行中的 JVM 持有旧 jar 的文件句柄，
   原地覆写会导致类加载读到半新半旧的字节码（`NoClassDefFoundError`），重启即可恢复。
