# 山月茶咖 · 新增功能实现路径手把手指南（建表 → 实体 → Mapper → Service → Controller → 验收一条龙）

> 本文回答三个问题：
> ① **新增一个业务功能，代码按什么顺序写**——从理解数据库表，到 Controller / Service / Mapper 各层怎么衔接，最后数据怎么落回数据库；
> ② **六个新增功能（F1/F2/F4/F5/F7/F8）各自的增量知识点**与推荐实现顺序；
> ③ **AI 模块做到什么程度、这个程度能实现什么**。
>
> 读者画像：分层理论已过（Controller 收·调·回 / Service 大脑 / Mapper SQL），第一次动手给骨架加功能。
> 配套文档：《新增功能教学文档.md》（各功能的 DDL / 接口契约 / 验收 curl 全在那里，本文不重复抄）。

## 一、总地图：写代码的顺序 ≠ 请求流动的顺序

分层是**运行时视角**（一次请求怎么流），动手加功能是**搭建视角**（从地基往上盖）。两个视角对上，每一步就都知道自己在干嘛：

```
搭建顺序（写代码时，自底向上）：
  ① DDL 建表 → ② entity 实体 → ③ Mapper 接口 → ④ Mapper XML → ⑤ Service → ⑥ Controller → ⑦ 重启验收

请求流向（跑起来后，自顶向下）：
  小程序 → ⑥ Controller 收请求 → ⑤ Service 干业务活 → ③④ Mapper 执行 SQL → ① 数据库
           ← 数据原路返回 ← entity 装数据 ← Result 信封封装 ←
```

| 步骤 | 放哪 | 一句话职责 | 照抄谁的 |
|---|---|---|---|
| ① 建表 | MySQL 执行 DDL | 定数据长什么样 | 教学文档各功能节直接复制 |
| ② 实体 | `shanyue-pojo` 的 `entity/` | Java 侧的"一行数据" | `Drink.java` |
| ③ Mapper 接口 | `shanyue-server` 的 `mapper/` | 声明"我要查什么" | `DrinkMapper.java` |
| ④ XML | `resources/mapper/` | 写 SQL 本体 | `DrinkMapper.xml` |
| ⑤ Service | `service/` + `impl/` | 业务大脑：校验、事务、抛异常 | `DrinkServiceImpl` |
| ⑥ Controller | `controller/user/` 或 `controller/admin/` | 收请求、调 Service、装 Result 信封 | `CategoryController` |

## 二、七步法走全流程（以 F1 轮播横幅为例，热身包，约 1 天）

### 第 ① 步：数据库层——先"读懂"DDL 再执行

```sql
CREATE TABLE banner (
    id          BIGINT       NOT NULL AUTO_INCREMENT,   -- 主键自增
    title       VARCHAR(64)  NOT NULL,                  -- 主标题
    subtitle    VARCHAR(64)  DEFAULT NULL,              -- 副标题（可为空）
    theme       VARCHAR(32)  NOT NULL,                  -- pine 松绿 / gold 鎏金 / terracotta 陶土
    image       VARCHAR(200) DEFAULT NULL,              -- 图 URL，空串=前端渲染渐变卡
    link_type   VARCHAR(16)  NOT NULL DEFAULT 'page',   -- 跳转类型
    link_url    VARCHAR(200) DEFAULT NULL,              -- 跳去哪个页面
    sort        INT          NOT NULL DEFAULT 0,        -- 排序
    status      INT          NOT NULL DEFAULT 1,        -- 0 下架 1 上架
    create_time DATETIME, update_time DATETIME,         -- ↓ 四列留给 @AutoFill 切面自动填
    create_user BIGINT UNSIGNED, update_user BIGINT UNSIGNED,
    PRIMARY KEY (id),
    KEY idx_banner_sort (sort)
);
```

**读表四问**（这是"理解数据库"的实义，不是背列名）：

1. **为什么留 create_time 等四列？** `@AutoFill` 切面按**固定字段名**匹配——实体里这四个名字一个字母都不能错，insert/update 时切面自动填值，代码里不用手动 set。
2. **为什么有 status？** C 端查询口径是 `status=1`——下架的横幅数据库里还留着（软删除思想），只是查询时过滤掉。
3. **为什么有 sort + 索引？** C 端按 sort 升序展示，`ORDER BY sort` 是高频操作，给它建索引。
4. **为什么图片可空？** image 空串时前端按 theme 渲染新中式渐变卡——**数据库容许"没图"，展示层有兜底**，解耦设计。

执行完 DDL 再跑种子 INSERT（3 条横幅），表里就有东西可查了。

### 第 ② 步：entity——表列的 Java 镜像

```java
@Data @Builder @NoArgsConstructor @AllArgsConstructor
public class Banner implements Serializable {
    private Long id;
    private String title;
    private String subtitle;
    private String theme;
    private String image;
    private String linkType;    // 数据库列 link_type ↔ 这里 linkType
    private String linkUrl;
    private Integer sort;
    private Integer status;
    private LocalDateTime createTime;   // 四个固定名，@AutoFill 按名字匹配
    private LocalDateTime updateTime;
    private Long createUser;
    private Long updateUser;
}
```

**关键机制**：`link_type` ↔ `linkType` 的翻译不用写一行代码——yml 里 `map-underscore-to-camel-case: true` 让 MyBatis 自动做蛇形→驼峰映射。规矩就一条：**字段名 = 列名的驼峰形式**。

### 第 ③ 步：Mapper 接口——声明"我要查什么"

```java
@Mapper
public interface BannerMapper {
    List<Banner> listEnabled();   // C 端：status=1 按 sort 升序
}
```

`@Mapper` 让 MyBatis 启动时给接口生成动态代理实现。**方法名 `listEnabled` 就是下一步 XML `<select id="...">` 的 id**——两把钥匙必须同名，对不上就是第一大报错 `Invalid bound statement`。

### 第 ④ 步：Mapper XML——SQL 本体

```xml
<mapper namespace="com.shanyue.mapper.BannerMapper">
    <select id="listEnabled" resultType="com.shanyue.entity.Banner">
        SELECT * FROM banner WHERE status = 1 ORDER BY sort ASC
    </select>
</mapper>
```

三个易错点：namespace 写**接口全限定名**（package + 类名）；id 与方法名一字不差；entity 在别名扫描范围内 `resultType` 可只写 `Banner`（VO 才要写全限定名）。

### 第 ⑤ 步：Service——业务大脑（F1 简单，但架子必须搭对）

```java
public interface BannerService { List<Banner> listEnabled(); }

@Service
public class BannerServiceImpl implements BannerService {
    @Autowired private BannerMapper bannerMapper;
    @Override public List<Banner> listEnabled() { return bannerMapper.listEnabled(); }
}
```

F1 业务太简单，Service 就是转发。**但架子必须搭**——将来 F4 券包的"一人一单"校验、`@Transactional` 事务边界、抛 `BaseException` 子类，全发生在这一层。Controller 直接调 Mapper 能跑，但那是业务逻辑漏到门口的写法，面试扣分点。

> 分层口诀：**Controller 收·调·回，Service 是大脑，Mapper 只管 SQL。**

### 第 ⑥ 步：Controller——挂到 /user/** 就自动有登录保护

```java
@RestController("userBannerController")   // bean 名带前缀，避免将来与管理端同名冲突
@RequestMapping("/user/banner")
@Tag(name = "C端-轮播横幅接口")
@Slf4j
public class BannerController {
    @Autowired private BannerService bannerService;

    @GetMapping("/list")
    @Operation(summary = "C端-横幅列表（status=1 按 sort 升序）")
    public Result<List<Banner>> list() {
        return Result.success(bannerService.listEnabled());
    }
}
```

**不用改任何拦截器配置**：路径挂在 `/user/**` 下，C 端 JWT 拦截器自动罩住它——没 token 直接 401 双通道弹回。方法体三拍：调 Service → 拿数据 → `Result.success()` 装信封。

### 第 ⑦ 步：重启 + curl 验收

```bash
TOKEN=<C端token>    # 生成方式见教学文档第 9 节
curl -s http://localhost:8080/user/banner/list -H "token: $TOKEN"
# 期望：3 条种子横幅，sort 升序
```

前端把 `USE_MOCK` 关掉后，首页轮播位立即从 mock 切到真接口——**mock 和真接口一字不差的契约**就是为了让这一刻零改动。

### 数据怎么落回数据库（闭环视角）

C 端读流程闭环：小程序发 GET → 拦截器验 token → Controller → Service → Mapper XML 的 SELECT → MySQL 返回结果集 → MyBatis 逐行 `new Banner` + 蛇形转驼峰 → List 原路返回 → `Result.success` 装信封 → Jackson 序列化成 JSON → 小程序渲染。

写流程闭环（管理端 CRUD，如插一条新横幅）：POST JSON → Controller `@RequestBody` 反序列化 → Service 校验 → Mapper `<insert>` → `@AutoFill` 切面在 insert 前把 createTime/updateTime 填进实体 → INSERT 落库 → 受影响行数原路返回。

## 三、三条安全底线（每个新功能都适用）

1. **当前用户 id 只从 `BaseContext.getCurrentId()` 取**（拦截器解析 token 后放 ThreadLocal），绝不信任前端传的 userId——防替别人下单/领券/签到；
2. **金额一律 BigDecimal**，服务端重算防篡改（前端传的价格字段只做展示）；
3. **写操作先查后写**（购物车"同款同规格只加数量"、领券"一人一单"），并发兜底靠唯一索引。

## 四、其余功能 = 同一条骨架 + 各自的"新东西"

| 功能 | 七步法之外的增量新知识 | 建议顺序 | 工期 |
|---|---|---|---|
| **F1 轮播横幅** | 无新概念，纯热身走通七步法 | 第 1 个 | 1 天 |
| **F2 会员等级** | 不建新表，`user` 表加 growth/points 两列；核心是**两个入账点**（支付成功 +2/元、签到 +5）与 `growth = growth + ?` 自增写法（天然并发安全，无 lost update） | 第 2 个 | 1 天 |
| **F5 每日签到** | Redis **BITMAP 三连**：SETBIT 记录第几天签到、BITFIELD 取整月位图、BITCOUNT 数连签——零新增 Java 概念，是 Redis 命令新玩法 | 第 3 个 | 1 天 |
| **F7 AI 点单** | RestTemplate 调外部大模型 API + 结构化输出解析 + 关键词降级兜底（详见第五、六节） | 第 4 个 | 2~3 天 |
| **F4 券包** | 技术天花板：Redis 防超卖 + 一人一单（三层防线）+ `@Transactional` 下单用券挂进订单事务 | 最后攻坚 | 3 天 |
| **F8 取餐推送** | 复用现成 `WebSocketServer`，只在订单状态流转处加两行 `sendToAllClient` | 收尾 | 0.5 天 |

推荐总顺序：**F1 → F2 → F5 → F7 → F4 → F8**。逻辑：先热身走通骨架 → 中等难度练"修改既有代码"（F2 入账点挂在别人的方法里）→ AI 主菜 → 券包攻坚 → 轻松收尾。每个功能 curl 验收过再动下一个。

## 五、AI 模块选什么程度：一级（+二级的 key 安全习惯）

先说结论：**做一级，别碰三级。**

| 级别 | 内容 | 成本 | 边际收益 |
|---|---|---|---|
| 一级 | Java RestTemplate 直调大模型 API + 降级兜底 | 1 天，**全是 Java**，照抄工程现成的 `RestTemplateConfiguration` 和 `WeChatProperties` 套路 | 简历/毕设的 AI 亮点够用 |
| 二级 | key 挪到环境变量，不进仓库 | 半小时习惯问题 | 面试必问题「key 怎么管理」的标准答案 |
| 三级 | FastAPI + LangChain 独立 Python 服务 | 2~3 天，Python + FastAPI + LangChain 三个陌生概念叠加 | 答辩架构图好看一点，面试官其实不太问 |

三级在架构上与一级不冲突（本工程只暴露 `POST /ai/order` 内部转发），**一级做完以后随时能补**——时间窗口紧张时先锁一级。

一级的调用链（写给简历/答辩用）：

```
小程序 → 你的后端 POST /user/ai/order
            → RestTemplate 组装 OpenAI 兼容请求（/chat/completions）
            → 大模型 API（baseUrl/apiKey/model 配在 application-dev.yml / 环境变量）
            → 解析 choices[0].message.content，截取 {...} JSON 段
            → 解析失败 → 关键词匹配降级，永远有话说
```

## 六、一级 AI 能实现什么 / 实现不了什么（诚实清单）

**能实现**：

1. **多轮对话**——请求体带 `history`，模型记得上一句（"再来杯便宜点的"能接住）；
2. **真菜单感知推荐**——后端实时查在售饮品拼进 Prompt，推荐永远真实存在，不会推下架的；
3. **结构化推荐卡片**——返回 `recommend`（drinkId/price/月售/理由/规格建议），前端「就点这杯」一键进购物车——**mock 阶段做不到的真下单闭环**；
4. **规格建议**——"建议少冰半糖"这类字段级输出；
5. **预算/口味/场景理解**——"20 以内冰的""晚上喝怕睡不着""饭后解腻"；
6. **降级兜底**——API 超时/返回乱格式时自动切关键词匹配，用户永远有回复。

**实现不了**（被问"局限"时的现成答案）：

- 流式打字机效果（一级非流式，等全文生成完才返回）；
- 跨会话长期记忆（history 只是前端传的当次对话）；
- RAG 知识库/向量检索（没上向量库）；
- Agent 自动下单（只推荐，用户确认才加购）。

每条都可反过来说："我知道边界在哪，这个业务量级上 RAG/流式是过度设计"——工程判断力比堆技术更显水平。

**简历 bullet 写法对照**：

| 别这么写 | 这么写 |
|---|---|
| ~~接入 AI 大模型接口实现智能点单~~ | 基于 OpenAI 兼容协议集成大模型 API 实现 AI 点单助手：后端持有密钥（key 不进仓库/前端不可见）、动态菜单摘要注入 Prompt、结构化输出解析（模型返回 JSON 不可信——代码块包裹/字段漂移/拒答，截取 + 异常全捕获）、关键词匹配降级兜底保证服务可用 |

**面试官 100% 追的四个问题**：

1. 为什么不让前端直接调大模型？→ key 会暴露在小程序包里，反编译即可盗刷；且无法控制 Prompt、无法注入菜单上下文。
2. API key 怎么管理？→ 环境变量/配置中心，yml 只留占位符，不进 Git。
3. 大模型返回的 JSON 不可信怎么办？→ 截取 `{...}` 段 + try 解析 + 字段校验，任何一步失败走降级——这是「对外部不可控依赖的隔离」设计，不是补丁。
4. 大模型挂了/超时怎么办？→ 同上降级链路，可用性 > 智能程度。

## 七、卡壳速查

| 症状 | 原因 | 解法 |
|---|---|---|
| 启动报 `Invalid bound statement` | XML 的 id 与接口方法名不一致 / namespace 不是全限定名 / XML 不在 `resources/mapper/` | 三把钥匙逐个核对 |
| curl 返回 401 | token 没带 / 过期 | 按教学文档第 9 节重新生成 |
| 查出来 createTime 全是 null | 实体字段名不是四个固定名，切面没匹配上 | 改成 `createTime/updateTime/createUser/updateUser` |
| yml 改了没生效 | 改的是 application.yml 而 profile 指向 dev | 改 `application-dev.yml`，或核对 `spring.profiles.active` |
| 新增数据但前端不显示 | 前端还在 mock 模式 | `config.js` 的 `USE_MOCK` 关掉对应路径 |
| 分页 total 对 records 不对 | PageHelper 的 startPage 与 Mapper 调用之间插了别的查询 | `PageHelper.startPage` 必须紧贴 `mapper.xxx()` |
